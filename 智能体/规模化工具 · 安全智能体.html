    工具的规模化应用

    在模块 1b 中，您将一个工具接入了智能体循环：模型请求调用一个具名函数，执行框架运行该函数，再将结果传回下一次模型调用。此处的往返过程并未改变，变化的是工具界面：模型必须从更多描述中作出选择，而每个工具背后都可能隐藏着更强大的能力。

    本页沿用这一约定，从本地函数逐步扩展到搜索后端和子智能体。将子智能体用作工具，就是将一个专注于特定任务的智能体封装在单一模式之后，使外层工作流可以分派任务，而不暴露其全部内部能力。Model Context Protocol (MCP) 为客户端提供了一套标准方法，用于发现并调用由其它进程提供的工具。请在能力边界处使用它，并先验证服务器、身份和权限范围。这两种模式都能精简主循环的工具列表，并为模块 2 中限定范围的工作流奠定基础。

    有多个工具可用时，模型会结合名称、描述、参数模式、对话及任何 tool_choice 约束来提出调用。各工具定义中的 description 说明该工具适用的场景。查看下方的工具规范节点可了解完整定义，或参阅函数调用指南了解请求格式。

    在不改变工具的情况下替换执行器？

    更换后端，同时保持工具约定不变

    此处以扁平的 mountRunCell 脚本运行相同循环，只有一处变化：执行器。之前的搜索会为多个匹配项分别返回一段简短说明。此后端则会从该术语的缓存术语表页面中，获取最佳匹配项的完整文章。模式和循环均未改变；只是 glossary_search 背后的数据源变得更加丰富。

    模型只能看到约定。它使用自然语言查询请求 glossary_search，并读取返回的内容，却不知道是哪个后端作出的响应。可以先使用简短说明索引，之后再替换为完整文章或实时搜索，无需修改循环。如果不同后端采用不同方式确定匹配项，准确性可能会发生变化，但约定仍然有效。

    需要 MCP 的发现和调用流程？

    使用 MCP 从独立服务器获取工具

    Model Context Protocol (MCP) 为工具服务提供了标准形式。智能体通过 tools/list 获取服务器的工具目录，并通过 tools/call 调用所选条目。这些工具运行在独立进程中，智能体启动时会连接该进程并进行查询。由于各处采用相同协议，智能体无需为每台服务器学习新的接口，即可连接更多服务器。当工具发现和传输需要共享协议时，请使用 MCP。如果执行框架已经知道能力的位置和调用方式，则使用本地函数、仓库技能或直接的 API 调用。

    发现过程也是信任边界。请将 tools/list 响应视为不可信输入。连接服务器之前：
    • 验证其身份，
    • 向用户显示所请求的能力，
    • 授予满足使用需求的最小权限范围，
    • 并将每项凭据绑定到该服务器对应的受众。
    对于远程连接和 OAuth 发现，请拒绝私有地址和链路本地地址，并验证每一次重定向。 MCP 安全指南要求客户端负责用户同意、token 处理以及服务器端请求伪造（SSRF）控制。

    下方的代码单元用纯 JavaScript 模拟一个小型 MCP 服务器，采用 MCP 定义的 JSON-RPC 格式，但不包含传输层。智能体获取工具列表，将模式交给模型，再把 tool_calls 分派回服务器的 tools/call 处理函数。循环仍会请求工具、执行工具，再追加结果；工具发现和分派则改由服务器接口处理。

    MCP 格式的工具服务器 · 发现 + 分派
    通过 tools/list 发现两个页面内 MCP 工具，再通过 tools/call 分派模型请求。智能体循环保持不变。
