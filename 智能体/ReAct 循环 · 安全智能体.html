    ReAct 循环

    基于语言模型构建的智能体同样会反复感知环境、进行推理并采取行动。模型会在行动之间用文字进行推理，这也是这一模式名称的由来。Yao et al. (2022) 将这种结合推理与行动的模式称为 ReAct。他们发现，将简短的推理轨迹与工具使用交替进行，在许多任务上比预先规划全部步骤或不经推理直接行动更可靠。

    工具是运行框架可代模型执行的代码：一个具有名称、描述、输入模式和返回值的函数。工具调用是模型发出的结构化代码执行请求。运行框架解析该请求、执行函数、追加结果，然后再次调用模型。

    大多数通用智能体框架都以这一循环为基础，LangChain 的 createReactAgent 也是如此。本模块的后续内容将逐步构建这一循环。

    • "stop" 表示模型已生成最终答案，循环可以将 content 返回给用户。
    • "tool_calls" 表示模型要求代码运行指定函数，追加结果后再回调模型。
    • "length" 表示答案尚未生成完毕，token 预算就已耗尽。
    • "content_filter" 表示安全分类器停止了输出。

    在现代 ReAct 中，一个简短的路由逻辑会读取该字段。如果模型请求使用工具，路由逻辑就会运行函数、追加结果并再次调用模型。如果模型已经停止，路由逻辑就会返回答案。

    模型读取工具结果后，可以修改原先的计划。每当工具返回意料之外的结果时，该结果都会进入下一轮推理，模型可以重新评估当前状况，再决定下一步操作。

    梳理模型、记忆、工具和路由？

    LLM 智能体的组成部分

    仔细观察智能体，您会看到 Lilian Weng 在 2023 年提出的组成结构。语言模型位于中心，周围是记忆、规划、工具以及触达外部世界的行动。

    在下方的工具循环中，这些职责分配如下：

    • 记忆是 messages[] 数组。
    • 规划发生在模型根据提供的上下文，选择下一次响应或工具请求时。
    • 工具是运行框架公开的函数。
    • 行动是运行框架执行的工具调用。

    运行框架负责维护消息并执行工具。其路由器读取 finish_reason，决定是处理工具请求，还是返回答案。

    这些模块彼此独立。可以单独替换模型、工具或路由；只要各模块仍遵守其它模块所依赖的契约，循环的其余部分就能继续运行。

    如果这个循环出现故障，请检查组件之间传递的值，确认是否存在以下情况：

    • 模型返回了错误的 finish_reason；
    • messages 数组中缺少一轮消息；
    • 工具执行器返回了意外的值；
    • 或者路由误读了信号。

    刚才 messages 数组内部发生了什么。
    当模型请求时钟时，循环会向 state.messages 中加入以下四项：
    • 系统提示词（第 0 轮），
    • 用户的问题（第 1 轮），
    • 一条带有 tool_calls 字段的 assistant 消息（第 2 轮，即请求），
    • 以及一条保存函数返回值的 tool 角色消息（第 3 轮）。
    下一次模型调用会收到这些消息，包括时钟结果。检查模型的响应，确认它是作答还是再次请求工具。这个不断增长的数组就是该智能体拥有的全部“记忆”。保存并重新加载该数组可以保留所提供的对话历史；外部事实和模型行为仍可能发生变化。
    需要上下文退化的证据和缓解措施？

    上下文退化：循环越长，为何理解效果越差

    上下文退化是指矛盾、过时的观察结果和不良约定不断积累在提示词历史中，最终导致模型下一次决策质量下降的趋势。这种影响还与信息所在的位置有关：Liu et al. (2023)的研究表明，模型可能无法充分利用埋藏在长上下文中部的信息。重要信号距离当前轮次越远，循环就越容易忽略它或产生与之矛盾的结果。

    常见的缓解方法会让每次决策尽量靠近其所需的证据：

    • 在循环积累观察结果之前先制定计划；
    • 委派子任务，让每个子智能体在较短的上下文中工作；
    • 或者在早期轮次成为负担之前对其进行总结。

    helpers.fetchRetry(url, opts)与 helpers.fetch 类似，并可接受一个有界的可选第三参数，例如 { retries: 2, timeoutMs: 120000 }。遇到 HTTP 429 时会遵循 Retry-After，其它情况下则报告最终的网络或 HTTP 结果。

    返回时钟循环画布，修改输入以进行这些比较。

    1. 即使模型不需要使用工具，也强制它进行工具调用。尝试提出一个工具确实无法回答的问题（“法国的首都是哪里？”），并观察第 1 步中的 finish_reason。它的值是 "stop" 还是 "tool_calls"？现在编辑系统提示词，要求模型必须先进行工具调用再回答（“您必须始终调用 get_current_time 一次，然后再回答。”）。模型是否遵从了要求？如果模型根据训练数据对另一个答案方向很有信心，这一现象说明系统提示词对模型的引导作用有多强？
    2. 统计需要工具的问题所用的步骤。“距离 17:00 UTC 还有多少分钟？”需要读取时钟并进行计算。运行几次，看看模型调用 get_current_time 一次、两次还是三次。为什么模型会重复调用已获取结果的工具？您会如何修改系统提示词来减少重复调用？
    这些比较能帮助我理解什么？

    第一组比较区分提示词指令和程序强制执行的控制流。先比较所请求的工具与 finish_reason，再判断指令是否得到遵循。仅有请求并不能证明时钟已运行。

    第二组比较关注每次额外工具调用是否提供了有用证据。检查时钟结果及其在 messages 中的顺序。如果顺序不清楚，请先返回时钟循环画布并展开跟踪记录，再修改提示词。不同运行的结果可能不同，请依据自己的跟踪记录解释结果。
