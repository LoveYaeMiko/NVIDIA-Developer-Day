# 模块 2 · 高级模式（工作流 / 索引智能体 / 深度智能体）

## 02a 工作流智能体

- **一句话主旨**：工作流智能体是由执行框架控制工作流的智能体系统——工作流由模型调用、确定性代码步骤、工具调用与专家循环组成，框架在每个边界决定哪些上下文可跨越、哪些部分可分叉、哪些结果进入下一阶段。
- **解决的问题**：单个 ReAct 循环只在一次性任务上够用；若下一步行动需在工具结果返回前确定、多个子任务可并行并共享结果、或路由应遵循规则而非最近一次观察，就该用工作流。原文以"重复扣费"对比：工作流把账单核验与账户历史检查分到独立分支，再汇总证据。
- **关键概念**：ReAct（推理与行动）——每步先读观察再选行动，工具路径在运行中形成；ReWOO（无观察推理）——工具运行前一次 LLM 调用写完整计划，确定性执行器并行执行全部工具，再第二次调用综合；固定枚举——封闭的允许标签列表，越界应拒绝或严格重试而非猜测；路由——分流后交给一个专用智能体；分发/扇出——同一共享输入同时发给多个专家；工厂——把角色、系统提示词、工具、调用方式参数化。
- **核心机制/步骤**：①ReWOO：Planner（`PLAN_SCHEMA` + `response_format:json_schema` 生成 3–5 个 queries）→ 执行器（纯 JS，`Promise.all` 并发 `helpers.webSearch(q,{maxResults:3})`，无 LLM 调用）→ 综合器（第二次调用，按 `[search N]` 引用），共两次 LLM 调用。②路由：`TRIAGE_SCHEMA` 输出 `{category,priority,summary}`，枚举 network/hardware/software/account 与 high/medium/low；纯 JS 以 `SPECIALISTS` + `Object.hasOwn` 选定专家提示词。③分发：一次 `helpers.webSearch(...,{maxResults:4})` 共享，`Promise.all` 调度三位专家，甘特图比较并发耗时与实际耗时。④工厂：`createSpecialist({role,systemPrompt,tools})` 返回 `run(input,helpers)`，校验 `finish_reason` 为 `stop`/`tool_calls`。
- **重要结论或陷阱**：每个智能体边界都增加模型延迟与路由逻辑、引入新的消息格式错误来源、把时间线变成分叉轨迹；拆分前先测量延迟与质量。`Promise.all` 任一分支被拒则整体被拒，故障隔离须显式处理。各单元以"目标/工单在规划期间变更即抛错"守护，防陈旧状态被综合；工厂只返回工具请求供检查，不执行它们。
- **交互式演示**：可改研究目标的 ReWOO 并行术语表研究（Planner、执行器、综合器、工作流图）；工单四枚举路由（分流 schema、分流 LLM、纯 JS 路由、专家 LLM）；共享搜索 + 三位专家并发并画甘特图；工厂构建算术辅导员与翻译员处理同一输入并排显示；动手尝试 · 实时分流路由。
- **承上启下**：B 部分把同一组合思路用于语料库（知识层成为智能体），C 部分由 planner 在全新上下文调度子智能体并把状态持久化到虚拟文件系统。

## 02b 索引智能体（RAG）

- **一句话主旨**：索引智能体通过开发者定义的工作流把工作流理念用于外部知识——预先嵌入并索引语料库，再检索匹配段落，依据范围受限的上下文包生成答案。
- **解决的问题**：检索系统必须返回回答问题所需的证据，而数据形态决定搜索方式。原文的检索阶梯是：仅凭模型上下文作答 → 传统 RAG 在每次生成前执行固定检索 → 智能体控制的检索，把检索当工具由循环决定是否再查。因推理 API 不允许更新权重，本课程用预训练模型走"先检索、后生成"两阶段（离线建索引 / 实时请求）。
- **关键概念**：上下文包——工作流中传递的一组完整且边界明确的上下文，是"先定数据包再选数据库"的规划方法；MCP——为检索提供发现与调用外部上下文来源的一种边界，何时检索与结果验证仍归运行时（配套边界还有 skills、A2A、UI 协议）；检索原语——非结构化文本用稠密向量 + 交叉编码器重排序，层次化文档用带父节点指针的树索引，结构化表格用语义层，图用图遍历（Cypher、GraphQL）；嵌入——学习得到的固定长度数值向量，令语义相近文本彼此接近；top-K 余弦——逐段算 `helpers.cosineSim` 后排序取前 K，向量数据库只是包装；小文本块 + 父文档——小块嵌入供检索、任意命中返回 FULL 父文档供生成；GraphRAG——索引阶段用 LLM 抽实体关系建图、检测社区并分别总结，查询时汇总社区摘要再归并，是结构上的 MapReduce 而非相似度查找。
- **核心机制/步骤**：非结构化路径四步：嵌入查询 → 搜 top-K 最近邻段落 → 拼进提示词 → 要求模型依据段落作答。链路：语料库 → 构建索引（`helpers.embed(corpus,{model:"nvidia/nemotron-3-embed-1b",inputType:"passage"})` 存 `{text,vector}`）→ 用户查询 → 以 `inputType:"query"` 嵌入、`cosineSim` 评分、排序、`slice(0,3)`；父文档拆句为块保留 `parent`/`idx`；最后封装 `retrieve(question, k)` 工具五步：嵌入一次建内存索引、JSON 模式声明、模型决定是否调用、Top-K 作为工具消息追加、第二次 LLM 调用作答。
- **重要结论或陷阱**：NVIDIA 嵌入模型用 `input_type`（"query"/"passage"）区分查询与段落，互换会改分数、降低质量却不报错。向量索引是嵌入输出的缓存，须防换模型后旧向量失效、提供商悄悄升级致分数漂移、两服务共享索引却固定不同模型 ID；规范固定值为 `nvidia/nemotron-3-embed-1b`。Top-K 永远返回 K 个段落即使分数都低；换成服务器端 FAISS+BM25+重排序前须验证结果与失败行为。
- **交互式演示**：检查一个嵌入（带符号分布、固定长度、归一化模长，及 input/model/input_type 契约）；构建内存向量索引（语料库、索引、查询、top-3）；检索子文本块返回父文档；将检索公开为智能体工具（含 LLM #2）；代码中的 Top-K 与 GraphRAG 对比；动手试用 · 实时检索（索引离线预建，仅问题实时嵌入）。
- **承上启下**：这些检索器回答答案存在于少量段落的局部问题；模块 2c 转向答案分散、规模超出单次对话容量的问题。

## 02c 深度智能体

- **一句话主旨**：深度研究智能体把同一思路用于证据规模超出单次对话容量的问题——运行时 planner 选出相互独立的分支，只向工作智能体提供原始问题、分配给它的任务及所需工具，同级历史不传入，最后由一个阶段综合各工作智能体保留的证据。
- **解决的问题**：单个 ReAct 循环把所有指令与观察留在同一段历史里，早期证据与每项新工具结果争夺注意力：溢出（超出上下文窗口）、上下文退化（相关证据权重不足，Liu et al.）、干扰（一个分支的推理分散下一分支的注意力）。
- **关键概念**：工作流边界——索引工作流由开发者定义、生成阶段接收有界检索资料包；深度研究工作流由 planner 在运行时创建分支，工作智能体接收特定任务上下文并存储证据；两处都可安放 ReAct 循环。规划/调研/保存/综合——拆成独立任务使范围先可检查；每个子智能体在全新上下文接一项任务；结果写入共享虚拟文件系统使证据在上下文结束后仍留存；编排器读证据生成可追溯的统一答案。循环转图——`createReactAgent({llm,tools})` 把 ReAct 循环变为显式模型节点与工具节点，图可独立运行或作为更大工作流的节点。子智能体——只拿到自己的任务与已保存文件列表。
- **核心机制/步骤**：①`ChatOpenAI` 封装任一同源 OpenAI 兼容入口，从 `helpers.getConfig()` 读 URL 与凭据，`invoke()` 返回 `AIMessage`，`.stream()` 逐步生成，二者都符合 `Runnable`。②导入 `ChatOpenAI, tool, createReactAgent, z`，用 `tool(fn,{name,description,schema:z.object({})})` 声明 `get_current_time`，编译图后 `agent.invoke()`，以 `helpers.viz.messageList` 呈现轨迹。③`state.vfs = {}` 作内存文件系统，`createWriteFile(dispatch)` 产出 `write_file`（带 dispatch 守卫）、`read_file`、`list_files`；随后规划类型化子任务、运行任务范围内工作智能体、整合草稿、显示观察到的工作流。
- **重要结论或陷阱**：全新上下文不是沙盒——上下文隔离分离分支推理，沙盒限制对操作系统的访问；浏览器制品无法使用 shell。第三个示例依模型知识撰稿：工作智能体有文件工具但无检索工具或来源，文件保存的是草稿而非独立核实的证据，文件名不是独立来源；`deepagents` 包为 Node.js 应用封装了类似模式。
- **交互式演示**：深度研究制品（240 行：提出研究问题、多个分支并行且各自流式传入可聚焦面板、最后带引用统一综合）；将 LangChain 连接到当前模型；构建 ReAct 图（加载依赖、声明类型化时间工具、编译、检查轨迹）；以保存的草稿构建工作流（模型客户端、共享草稿工具、规划类型化子任务、运行工作智能体、整合草稿、显示工作流）。
- **承上启下**：本页收尾模块 2，下一节为模块 3a 快速入门；参考资料含 Liu et al.《Lost in the Middle》、LangChain 深度智能体、NVIDIA AI-Q 深度研究技能及 blueprint、Kosmos。

## 模块级要点

- **三条主线/递进关系**：02a 确立"执行框架控制边界、数据流与扇出"的骨架（ReWOO 先规划后并发执行、固定枚举路由、共享输入分发、工厂声明专家）；02b 把同一组合思路从"其它智能体"转向"语料库"，让知识层成为通过查询接口封装数据的智能体（上下文包 → 检索原语 → 嵌入 → top-K 余弦 → 小文本块+父文档 → 包成工具 → GraphRAG）；02c 把边界推到超出单次对话容量，控制流从循环升级为图。三者共同点：开发者先定义上下文包与边界，模型只负责边界内该由模型决定的部分。
- **术语表**：
  - 工作流智能体 —— workflow agent；推理与行动 —— ReAct；无观察推理 —— ReWOO
  - 分流 / 路由 —— triage / routing；固定枚举 —— fixed enum（`enum:["network","hardware","software","account"]`）
  - 分发（扇出）—— fan-out；工厂 —— factory（`createSpecialist({role,systemPrompt,tools})`）
  - 术语表搜索 —— `helpers.webSearch`；流式对话 —— `helpers.chatStream`
  - 上下文包 —— context packet；嵌入 —— embedding（`helpers.embed`，`nvidia/nemotron-3-embed-1b`）
  - 余弦相似度 —— `helpers.cosineSim`；top-K —— top-K；父文档 / 文本块 —— parent document / chunk
  - 检索工具 —— `retrieve(question, k)`；社区摘要 —— community summary；全局问题 —— global question
  - 智能体图 —— `createReactAgent({llm,tools})`；虚拟文件系统 —— `state.vfs`（`write_file` / `read_file` / `list_files`）
- **"继续学习之前"练习题要点**：
  - 02a-1：ReWOO 的 planner 看不到工具结果，若后续查询需用前一项结果中的事实就会失效，应切换回 ReAct。
  - 02a-2：枚举之外的类别应拒绝或在更严格指令下重试而非猜测；仅靠 JSON schema 不够，还需应用端验证（如 `Object.hasOwn`）。
  - 02a-3：工厂已参数化角色、系统提示词、工具与调用方式，第五个参数宜为"输入含义模糊时如何守住领域边界"。
  - 02b-1：`input_type` 的非对称性让问题嵌入与能回答它的段落嵌入对齐，提供纯对称余弦方法没有的能力。
  - 02b-2：增删改语料或更换嵌入模型/配置需完整重建索引；新问题只需生成一个新的查询嵌入。
  - 02b-3：Top-K 总会返回 K 个段落即使分数都低，入提示词前应检查相关度得分这一信号。
  - 02c-1：每个子智能体只含原始问题、自己的任务与所需工具，排除其它分支的历史与推理。
  - 02c-2：保存结果使证据在工作智能体上下文结束后仍留存，避免对话记录膨胀带来的溢出与干扰。
  - 02c-3：上下文隔离分离分支推理、防上下文退化与干扰；沙盒限制对操作系统的访问（原文未给出沙盒对应的具体故障类型）。
