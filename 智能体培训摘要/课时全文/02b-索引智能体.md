**▸ 追溯 RAG 从联合训练到检索的演变？**

## RAG 的起源：一个经过端到端训练的系统

当Lewis 及其同事在 2020 年将此方法命名为检索增强生成时，他们针对任务共同训练了检索器与生成器。请先从左到右阅读图示，再观察上方的箭头。

*原始架构出自 Lewis et al. 2020，其中包含如今构建的大多数系统都会省略的顶行反向传播标签。*

该设计的关键在标有“通过 q 和 pθ进行端到端反向传播”的箭头中。一个损失函数会同时更新两部分。查询编码器学习生成器可以利用哪些段落，生成器则学习更多依赖检索到的证据，而非自身记忆。

检索器最初就是模型的一部分，并由需要执行的任务塑造。直到很久以后，人们才将其描述为置于模型之前的搜索工具。

## 使用预训练模型进行 RAG

推理 API 不提供更新模型权重的访问方式。要共同训练自行托管的检索器与生成器，就需要模型权重、训练数据与计算资源。

本例的工作流使用预训练模型，不更新其权重。检索器选择段落并将其加入生成提示词。您可以调整检索并检查结果，而不必训练生成器。

## 您将构建的“先检索、后生成”工作流

检索器在权重固定的模型接收输入前执行检索，分为两个时序：先构建索引，再利用索引处理实时请求。下图呈现这两个阶段。

*本课程复现的两阶段工作流参考了 Hayden Wolff, RAG 101（NVIDIA，2023 年）和 Amit Bleiweiss, 构建 RAG 工作流的建议（NVIDIA，2024 年）。*

离线：对每个段落生成嵌入并存储，以便快速查询，一次性构建索引。

实时：对问题生成嵌入，检索 top-K 个段落，再将这些段落与问题一同传给模型。

本页接下来的内容将逐阶段构建实时路径。

**▸ 选择数据包、边界和数据结构？**

## 选择存储方案前，先定义上下文包

选择检索原语之前，您应先定义一个上下文包。上下文包是您打算在工作流中传递的一组完整且边界明确的上下文。

- 对于简单的单轮问答系统，上下文包可以很小：用户问题、为回答该问题而检索到的少量文本块，以及答案本身。
- 对于自主智能体，上下文包是它在多个轮次间携带的工作记忆。其中存储智能体的约束、先前决策、阶段性结果、可用工具接口和运行规则。
- 对于任意 Index 智能体，智能体返回的上下文包可能只包含检索到的上下文块，以及相应的文本块来源、相关性分数和可能生成的摘要。另一个独立的内部上下文包可以采用上文扁平的实时请求处理工作流，也可以采用 ReAct 风格的循环：反复检索、判断检索结果的相关性并重试，直到积累足够的上下文。

上下文包原则是一种规划方法：先定义上下文包，再选择数据库。下表帮助您检查候选的基础机制能否提供任务所需的上下文包。

## MCP 在检索系统中的定位

MCP 为检索系统提供了发现和调用外部上下文来源的一种边界。智能体仍需要运行时来决定何时检索、验证结果，并将结果与当前任务状态的其余部分组合起来。同一系统的其它部分可以通过其它边界传递： skills 封装可复用的能力说明，A2A 可以将工作路由给远程专家，而 UI 协议可以将生成的状态流式传回应用。

## 根据数据形态选择合适的检索原语

下表列出可供不同数据形态考虑的检索方法。请根据有代表性的问题、各个答案所需的证据与获取证据的成本来选择，并评估返回结果是否覆盖这些证据。

| 形态 | 示例 | 可考虑的方法 |
|---|---|---|
| 非结构化文本 | 文档、文章、代码注释、文字记录 | 稠密向量 + 交叉编码器重排序 |
| 层次化文档 | 法律合同、技术手册、嵌套规范 | 带父节点指针的树索引 |
| 结构化表格／受治理表格 | 客户记录、财务账簿、HR 表 | 构建在事实来源之上的语义层 |
| 关系／图 | 组织结构图、代码依赖关系、知识图谱 | 图遍历（Cypher、GraphQL、自定义方案） |

非结构化文本示例会从语料库检索段落，并要求模型根据这些段落回答。请检查答案是否有这些段落支持。

每个请求都会经过相同的四个步骤：

- 将查询嵌入为向量。
- 在段落索引中搜索 top-K 个最近邻段落。
- 将这些段落拼接到提示词中。
- 生成答案，并在指令中要求使用这些段落。

其他检索器可以使用关键词搜索或结构化查询。请根据数据选择检索方法，再检查它为生成器提供了哪些证据。

## 将文本嵌入为向量以进行相似度搜索

这个向量检索器用嵌入表示段落和查询。嵌入是通过学习得到的文本数值表示，形式为固定长度的向量，使语义相近的文本在向量空间中彼此接近。这带来两项实际用途：

比较：对两个向量计算余弦相似度，只需一次点积和两个向量的模。

存储：向量索引按照文本在该空间中的位置进行组织，以便高效执行最近邻搜索。

两项操作都使用嵌入模型，本课程通过helpers.embed调用它。浏览器会通过课程中继服务发送你的文本。课程主机提供服务凭据；如果配置的嵌入服务不可用，请检查返回的错误。

嵌入 API 契约。

嵌入 API 入口接收包含三个字段的 JSON 请求，并返回一个向量数组：

- input 是待嵌入的文本批次，类型为 string[]。
- model 指定嵌入模型，类型为 string。
- input_type 的值为 "query" 或 "passage"。
- 响应包含一个 data 数组，其中每个条目都包含embedding，其类型为 number[]。

NVIDIA 嵌入模型使用input_type区分查询与段落。其检索训练旨在让问题与能回答问题的段落匹配。将"query"与"passage"互换可能改变分数并降低检索质量，而不会造成 API 错误。请检查类型，并评估返回的段落。

故障模式：陈旧的嵌入。

向量索引是嵌入模型输出的缓存。生产系统必须防范以下几种特定故障：

- 一旦更换嵌入模型，所有缓存向量都会失去意义，直到您重新嵌入每个段落。
- 提供商悄悄升级模型，分数随之漂移，却不会触发任何错误。
- 两个服务共享同一索引，却固定使用不同的模型 ID；该索引会向其中一个服务返回毫无意义的结果。

可靠的索引会为每个缓存向量同时固定嵌入模型 ID，并拒绝混用不同版本。本课程的规范固定值是nvidia/nemotron-3-embed-1b，由 integrate.api.nvidia.com 通过课程代理提供服务。

## 搜索小文本块，返回其父文档

基础的 top-K Index 智能体需要权衡召回率与精确率，这不是任何嵌入模型能够解决的问题。您必须在短文本块和长文档之间做出选择：

- 短文本块让嵌入聚焦于较小的段落，但可能省略回答问题所需的上下文。
- 长文档包含更多上下文，但将多个主题放进同一个嵌入，可能削弱它与特定问题的匹配程度。

一种做法是建立两层索引。先为小文本块生成嵌入以供检索，再由匹配的文本块选出父文档，为后续生成步骤提供更多上下文。

下面的练习使用三个父文档构建这种模式。每个文档都拆分为简短的句子块，查询则返回匹配的父文档。

检索子文本块，返回父文档

将三个父文档分别拆分为简短的句子块，然后对其进行嵌入并建立索引。命中任意文本块后都会返回 FULL 父文档，从而兼顾短文本块的精确性与完整文档的上下文。

## 将索引封装为由模型决定是否调用的工具

检索索引本身只会在收到查询时给出答案。将其封装为模型可选择调用的工具后，它便成为一个索引智能体，由模型判断是否值得执行检索。下面的单元格分五步实现这一过程：

1. 语料库只需嵌入一次，并保存在内存索引中。
2. 使用 JSON 模式声明一个 retrieve(question, k) 工具。
3. 智能体接收用户的问题，并决定是否调用该工具。
4. 如果调用，系统会在索引上执行余弦检索，并将 Top-K 段落作为工具消息追加到上下文中。
5. 第二次调用 LLM，依据检索到的段落撰写最终答案。

您可以保留工具接口，将内存中的余弦搜索替换为服务器端 FAISS+BM25+重排序流水线的执行器。在循环中使用前，请验证其结果和失败时的行为。

## 其它三种模式如何构建

您刚刚构建了从语料库到答案的非结构化文本路径。这里列出其它三种模式，帮助您在实际场景中识别它们并选用正确的基础技术。每种模式都有成熟的生产实现方式，概要如下。

- 层次化文档。使用保留标题层级的文本分块器，并结合原子化表格提取、父级指针以及用于结构搜索和语义搜索的双索引。为提高召回率，对小型子文本块建立索引；命中后获取其所属父级内容，使模型能够同时阅读匹配的条款及其所在章节。
- 面向图形和图表的页面图像检索。采用双向量配置，同时嵌入渲染后的页面图像及其文本，使查询在答案位于图形或幻灯片中时也能将其检索出来。
- 结构化表格与受治理表格。本课程不构建此模式。标准的生产模式是在智能体和行级数据之间设置语义层，仅公开该数据包所需的精选指标。
- 关系数据与图数据。智能体调用图遍历工具（Cypher、GraphQL 或自定义工具），而不是向量存储。返回的数据包是一个子图，其中的显式边会随数据一起进入提示词，从而将实体间的关系完整传递给模型。

**▸ 探索使用 GraphRAG 进行全语料库检索？**

## 当 Top-K 并不适用时：GraphRAG 与全局问题

本页介绍的每种检索器都用于回答局部问题。这类问题的答案存在于少量段落中，Top-K 相似度检索可以找到这些段落供模型阅读，例如询问合同对终止事项有何规定，或哪篇论文提出了HyDE。另一类问题的答案根本不存在于任何单独段落中。例如，询问一千份文档的主要主题时，答案过于分散，不会存在于某个段落里，只有从整个语料库中才能归纳出来。

当 K 设为 3 时，top-K 会从这个含有一千个段落的示例中返回三个匹配段落。生成步骤只收到这些选定的段落，它们可能未覆盖语料库其他位置的主题。GraphRAG（Edge et al. 2024）会改变问题的处理方式，而非提高 K。它会在索引阶段使用 LLM 来：

- 读取语料库，将实体及其相互关系提取到知识图谱中；
- 检测图中的社区，即由紧密连接的实体组成的集群；
- 分别总结每个社区。

随后，在查询时通过汇总相关社区的摘要来回答全局问题，再将这些局部答案归并为一个答案。这个过程是在结构上执行 MapReduce，而不是按相似度进行查找。
