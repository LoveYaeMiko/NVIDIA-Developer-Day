    智能体

    智能体是指能够在任何有意义的层面上与环境交互的实体。从这个意义上说，处理日常事务的人是智能体，将房间维持在设定温度的恒温器，以及在车流中行驶的自动驾驶汽车，同样也是智能体。

    它们都会通过传感器感知环境，并通过执行器对环境采取行动。每次行动都会影响下一次观察，因此感知、推理和行动构成一个持续运转的循环。只要智能体仍在交互，这个感知、推理与行动循环就会持续。您将构建的所有智能体都采用同一循环，区别仅在于它们能感知多少信息，以及行动能够影响多大范围。

    循环的三个环节

    循环每运行一轮都会经过三个环节，每个环节都有直观的名称和明确的职责。

    感知负责收集智能体能够获知的信息，推理决定要做什么，行动则改变环境。感知和行动通常源自现有的交互模型，无论它控制的是吸尘器、Web 自动化程序、游戏实体还是人形机器人。推理步骤可以在不改变这一边界的情况下发生变化，从而将能力与触达范围区分开来。

    探索智能体循环和经典架构？

    如果您想查看具体示例和更完整的架构分类，请打开本节。

    • 感知为智能体提供它对环境的全部认知。恒温器只读取一个数值：当前温度。自动驾驶汽车则融合摄像头、雷达和地图信息，构建道路模型。感知所捕获的信息就是智能体能够利用的全部信息，因为后续环节都不会直接接触现实世界。感知中的盲区会成为智能体其它部分无法弥补的盲区。
    • 推理将感知结果转化为决策，不同智能体的推理方式可能大不相同。恒温器只需将当前温度与目标温度进行比较，而国际象棋引擎会搜索数百万种走法，自动驾驶汽车则会运行学习得到的策略。您将在此构建的智能体通过调用语言模型进行推理，而本课程后续添加的几乎所有能力（工具、记忆和规划）都依托于这一步。
    • 行动会改变智能体自身及其它参与者所处的环境。行动可以简单到切换继电器，也可以复杂到操控汽车。后续页面会将暴露给模型的代码称为工具，因为从模型的角度看，它只是另一种可用的行动。调用工具，就是将执行这段暴露的代码作为行动。行动空间也界定了智能体能力所及的最外边界，因为无论推理能力多强，智能体都只能通过行动空间影响现实世界。
    推理步骤可以替换。感知和行动并不关心二者之间采用的是哪一种决策函数。简单规则、决策树、搜索程序或神经网络都可以驱动同一个循环。只需构建一次固定的循环框架，就能清楚区分两个问题：推理能力有多强，以及行动能够影响多大范围。

    经典智能体设计的区别在于决策步骤。Russell 和 Norvig 的 Artificial Intelligence: A Modern Approach 将这些设计排列成一条谱系：从仅具备反射机制的智能体，到能够改进自身规则的学习型智能体。本课程先从固定逻辑入手，再加入语言模型和经过设计的上下文，逐步构建基于模型、以目标为导向的循环。后续模块会让这一循环在不断变化的状态下持续运行，这正是学习型智能体赖以发展的模式。

    推理调用 LLM 后会发生什么变化

    可以像调用其它函数一样调用聊天补全接口：向它传入消息列表和模型名称，它会返回一条助手消息及元数据。

    关于 chat()。这是课程提供的封装函数，您稍后将在本页下方实时运行它。下面的代码片段会预先展示其调用形式和返回字段，让您在进入可运行的代码单元时已熟悉这些名称。 
    const reply = await chat({
  model:    "nvidia/nemotron-3.5-lightning-30b-a3b",
  messages: [{ role: "user", content: "Hi" }],
});
// reply.choices[0].message  → { content, reasoning_content }
// reply.choices[0].finish_reason → "stop" | "tool_calls" | "length"

    该函数的三个特征决定了基于它构建的智能体必须如何运行：

    • 各次调用不共享状态。两次请求之间，服务器不会替您保留任何内容。如果希望模型记住上一轮对话，您需要再次发送该轮内容。对话的“记忆”就是由代码维护，并在每次调用时重新发送的消息列表。
    • 推理输出不一定会出现。部分模型与模式会在 reasoning_content 中返回推理文本，其他模型则只返回答案内容或工具请求。请检查实际返回的字段。循环会读取 content、结束原因与工具请求，再决定下一步。
    • finish_reason 是循环的退出条件。 "stop" 表示模型已生成最终答案。"tool_calls" 表示模型希望代码运行指定函数，并将结果返回给它。 "length" 表示模型尚未完成时，token 预算已耗尽。决定下一步之前，请同时检查这个字段、返回内容和工具请求。
    比较不同 API 在何处保存对话状态？

    本课程始终使用 Chat Completions API：您需要在自己的代码中以 messages[] 数组保存对话，并在每一轮重新发送完整数组。较新的 Responses API 则可以在服务器端保存对话线程，因此您只需发送新输入以及对上一轮的引用。无论采用哪种方式，模型在各次调用之间都保持无状态且不会发生改变。对话存在于模型之外，由代码或服务器维护相应状态。

    在本地绘制循环

    在迷宫示例中，控制器会构建 chat() 请求，并在执行返回的移动指令前进行验证。以下阶段逐步说明这次交互。

    • 局部采样。代码读取环境的一部分。在此示例中，读取的是迷宫中当前所在的格子及其有效移动方向。根据所选控件，请求还可以包含完整地图和此前的轮次。
    • 局部感知。将采样数据组织成完整、经过设计的上下文，其中包括系统提示词、持续累积的 messages[] 历史记录、先前的工具结果，以及刚刚采样的数据。此示例在发送给模型的消息中，用文本描述迷宫。
    • 局部行动。模型将这些文本映射为更多文本：一个意图信号。理想情况下，它是类似 { "move": "east" } 的类型化工具调用，而不是自由文本。该意图只是在请求执行动作，本身从不执行任何操作。代码会读取它，在验证后对环境应用一次范围受限的更新 (doMove(...))。
    • 局部影响。更新会改变环境。模型内部不会持久保留任何内容。唯一持久的状态是环境，以及代码将重新构建的上下文。下一轮的局部采样会读取已改变的环境，随后循环再次开始。

    在此示例中，chat() 接收描述迷宫的文本，并返回请求执行的移动指令。控制器提供观察结果、验证请求，并改变迷宫状态。模型调用本身不会执行移动。

    请检查两个边界：提供给模型的上下文，以及代码在执行所请求的动作之前进行的验证。

    迷宫请求可以包含完整地图和之前的轮次。打开请求详情，查看实际包含的上下文。模块 1b 将使用显式的消息数组构建工具循环。

    继续学习之前

    只需编辑上方 LLM 迷宫单元格中的一个设置并重新运行，即可回答每个问题。

    1. 比较对话历史。设置 includeHistory:false，使用相同的配置组合与迷宫重新运行。与开启对话历史时比较分支顺序、岔路口的决策及经过时间。两次运行中，控制器都会保留已访问的单元格与返回路径。
    2. 移除 DIRECTIVE 中的策略提示。删除优先选择未探索分支而非已访问单元格的那一行，使用相同的配置组合与迷宫重新运行。比较分支顺序、岔路口的决策及经过时间。控制器仍会排除已访问的分支；请重复运行，检查差异是否持续出现。
    3. 比较模型配置组合。先使用 model:"direct"，再在相同迷宫中比较 model:"reasoning" 和 model:"omni"。检查每个请求的模型、token 预算、温度及推理设置。这些配置组合会同时改变多项设置；比较分支顺序及延迟时，不要将所有差异都归因于模型身份。

    OpenClaw 网关
    helpers.openclawBootstrapRequest(path)通过从模块 3a 标准化连接中选择的提供商读取 /api/agent 或 /healthz。对于 Pomerium，这些固定 API 入口会通过终端 WebSocket 从可启动实例的 loopback 读取；系统先尝试已登录的浏览器会话，再尝试获准的提供商专用中继。返回响应元数据和解析后的 JSON，不暴露任何访问凭据。
    helpers.openclawChat(message, {session, onToken, onTool, view})通过 /cli/gateway WebSocket 向实时 OpenClaw 智能体发送一轮聊天并流式接收回复。可启动实例 URL 和 token 从 OpenClaw 探测结果（Kickstart 页面）中读取。传入 view（即 mountChatUI 的 ctx.view）后，它会完整驱动可观察的执行过程：回答文本、按执行顺序排列的每个工具或命令调用标签（包含参数和完整结果，并标记错误），以及网关报告的上下文 token 预算。也可以传入 onToken(delta) 和 onTool(name,{id,args}) 自行处理事件。网关不会传输推理通道，因此页面不显示推理内容。多轮对话应复用同一个 session。它是 chat()/createReactAgent 对应的网关辅助函数。
    helpers.courseTurn(state, helpers, session, message)通过此工作流已建立的网关连接发送一个轮次，等待已确认运行的最终聊天事件。传入当前单元格的辅助函数，以便使用本次运行的停止按钮，并记录事件和创建的会话。
    helpers.openclawLoopbackProbe(path, opts?)通过 Pomerium 可启动实例的终端读取获准的 OpenClaw 引导端点，而不暴露浏览器 cookie。

    helpers.runOpenClawConnectionAudit(opts)依次测试可启动实例的元数据、网关、终端和健康路由，并返回脱敏证据。

    helpers.refreshOpenClawGatewayToken(opts?)从已验证的智能体元数据刷新网关 token，并仅保存在本标签页中。

    运行控制
    helpers.signal本次运行对应的 AbortSignal，已连接到停止按钮。helpers.delay、helpers.chat 和 chatStream 会自动使用它。将它传给 helpers.fetch 或您自己的 WebSocket 清理逻辑，确保学习者按下停止按钮后，长时间运行的任务能够真正取消。
    helpers.delay(ms)等待指定时间，同时允许学习者停止正在运行的单元格。CanvasFlow 和 RunCell 会自动将此辅助函数连接到停止按钮；只有等待过程属于其它生命周期时，才需要传入另一个 AbortSignal。
    追踪与日志
    helpers.trace(name, attrs)向每个 CanvasFlow 独立的追踪存储中写入一个符合 OTel 结构的 span 事件。任何实际执行工作的步骤都应记录，而不仅限于 LLM 调用。后续节点可以读取 state.__trace，查看所有已写入事件。
    helpers.log(...args)向当前单元格的日志区域追加内容。普通值以文本形式追加，对象则渲染为带语法高亮的 JSON。CanvasFlow 和 RunCell 共用以下接口：log(...args)、log.h(title)、log.json(label?, value)、log.kv(object)、log.details(summary, body)、log.html(html)、log.svg(svgString)、log.draw(W, H, body, opts) 和 log.clear()。

    helpers.viz.chat(turns, opts?)以不同颜色的气泡显示聊天记录。turns 是 [role, content] 对的数组；role ∈ {user, assistant|ai, system, tool}。opts.maxChars 用于限制每轮显示的字符数。
