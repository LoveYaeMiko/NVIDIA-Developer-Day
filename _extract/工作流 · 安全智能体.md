# 工作流智能体

单个 ReAct 循环可以处理大多数一次性任务，但更困难的问题有时需要一种结构，在下一个工具结果返回之前就决定要执行的工作。工作流智能体 是指由执行框架控制工作流的智能体系统：该工作流由模型调用、确定性代码步骤、工具调用和专家循环组成。以下情形适合采用这种结构：并行运行的子任务可以共享结果；可以在工具运行前制定计划；或者路由应遵循规则，而不是取决于最近一次观察结果。

执行框架可以围绕一次模型调用、一个确定性步骤、一个专家循环或一组并行分支界定工作流范围。在每个边界处，执行框架都会决定哪些上下文可以跨越边界、哪些部分可以分支，以及哪些结果将传入工作流的下一阶段。扇出和固定路由让这种控制清晰可见，同时保留上一页介绍的 ReAct 循环。

对于“同一订阅被重复扣费”这一问题，单个 ReAct 循环会先读取每次查询的结果，再选择下一步操作。结构化工作流可以将账单核验和账户历史记录检查路由到相互独立的分支，然后汇总各分支的证据。如果下一步取决于最新的观察结果，请使用循环。如果在执行前就已明确各个分支及其汇合方式，请使用工作流。

## 两种关键模式的区别在于模型何时做出决定
响应式 · 逐步执行

### ReAct（推理与行动）

在每一步中，模型都会先读取最新观察结果，再选择行动并运行工具；随后评估返回结果，再次作出选择。智能体会对上一次工具调用的返回结果作出响应 ，因此工具使用路径是在运行过程中逐步形成的。当执行路径取决于中间结果时，ReAct 表现出色；而当多个步骤本可同时运行时，它的表现则较弱。 论文：Yao et al., 2022 。
审慎规划式 · 先规划再执行

### ReWOO（无观察推理）

在任何工具开始运行之前，模型会通过一次 LLM 调用预先写出完整计划。随后，确定性执行器通常会并行运行计划中指定的所有工具，再由第二次 LLM 调用读取返回结果并进行综合。由于计划始终看不到工具结果，模型是在“无观察的情况下推理”。因此，当各步骤彼此独立时，ReWOO 表现出色；而当后续步骤需要根据前序结果作出响应时，它的表现则较弱。 论文：Xu et al., 2023 。

*ReAct 在每次工具调用之间穿插一个推理步骤，先对每项观察结果作出响应，再决定下一步行动。*

*ReWOO 在任何工具运行前写出完整计划，无需再次询问模型便可执行各个步骤，最后统一综合一次。*
ReAct 循环中的工具可以运行预先规划的流水线。如果规划中的某个阶段需要根据中间结果调整，也可以调用 ReAct 循环。采用固定流程的阶段则可作为普通函数运行，下方的执行器就是如此。

## 单一循环何时优于拆分成多个智能体
每个智能体边界都会增加模型调用延迟和路由逻辑，还会引入一个新的消息格式错误来源，并将清晰易读的时间线变成一条向多个工作单元分叉的执行轨迹。

比较新增的调用与协调成本，以及它们能完成的工作。不同的提示词或工具可帮助专家聚焦；独立工作可同时进行。决定是否拆分任务前，先测量延迟与回答质量。故障隔离也需要明确处理：以下示例使用Promise.all ，只要任一分支的 Promise 被拒绝，整体 Promise 就会被拒绝。

## 针对 NVIDIA 术语表运行 ReWOO 工作流

以下单元针对 NVIDIA 术语表运行 ReWOO 工作流，并对计划要求的每次检索使用helpers.webSearch （您在模块 1c 中接触过的术语表排序搜索）。术语表浏览器 会显示此搜索所用的完整索引，还可让您运行 planner 可能生成的任何查询：

Promise.all 是 JavaScript 中用于启动多个 promise 并等待它们全部完成的辅助函数。在这里，它只负责实现并发：既不调用模型，也不决定要运行哪些搜索。

1. Planner。一次受 schema 约束的 LLM 调用会生成包含 3 至 5 个搜索查询的 JSON 列表。
2. 执行器。使用纯 JavaScript。每个查询都通过 Promise.all 并发运行，此阶段不进行 LLM 调用。
3. 综合器。第二次 LLM 调用读取所有结果并撰写简报，同时按索引引用每项搜索。

总共进行两次 LLM 调用，外加 N 次并行术语表搜索。编辑研究目标，观察 planner 的查询列表如何变化。
ReWOO 会预先写出完整计划，因此所有工具都无需再次询问模型即可运行，最后通过一次综合调用完成任务。编辑节点 1 中的目标并重新运行。

## 使用固定枚举将工单路由给一个专用智能体

路由是多智能体的另一种组织方式：分流智能体对输入进行分类，再将其交给一个专用智能体。由于分类器必须输出固定枚举中的一个类别，因此输出需要遵循严格的约定。固定枚举 是一个封闭的允许标签列表；如果模型返回其它任何值，路由都应拒绝该结果或在更严格的指令下重试，而不能自行猜测。下游每个专用智能体都有范围明确的系统提示词，无需查看分流智能体的推理过程。

*包含四个值的枚举只会选择一个专用智能体来处理请求。*
第一次受 schema 约束的 LLM 调用会生成 {category, priority, summary}；一个纯 JS 路由根据类别选择专用智能体的系统提示词；第二次 LLM 调用则依据该提示词撰写回复。

## 将一个共享输入同时分发给多个专用智能体

ReWOO 工作流在设计上就是并行的，因为它规划的每个查询都会针对术语表并发运行。另一种更常见的并行模式是将一个共享输入分发给多个专用智能体；每个智能体都有自己的系统提示词，并且全部同时运行。在执行轨迹中，总耗时取决于最慢的专用智能体，其它智能体则在这段时间内重叠运行。甘特图会显示每个专用智能体的运行时长，并且所有智能体共享一项网络搜索结果，从而将成本控制在一定范围内。
一份共享搜索结果会分发给三位使用不同系统提示词的专家，并由 Promise.all 并发调度，因此总实际耗时取决于最慢的专家，而不是三者耗时之和。

## 通过工厂声明专用智能体，无需逐个手动编写

上方每个专家都定义了角色标签、系统提示词、工具列表与调用方式。下方的工厂会将这些输入公开为参数，让另一个专家能复用相同的构建方式。

- 角色。用于日志记录和路由的简短标签。
- 系统提示词。行为约定：它要做什么、拒绝做什么，以及如何组织回复。
- 工具。模型可请求的可选结构描述。这个单次调用封装会返回请求供您检查，不会执行它们。
- 调用契约。specialist.run(input) 返回一次模型响应，包含结束原因与任何工具请求。

下方单元格使用同一个工厂创建两个专家：算术辅导员与翻译员。两者收到相同的输入，响应并排显示。
工厂函数接收 (role, systemPrompt, tools) 并返回可调用的专家，再让由它构建的两位专家处理同一个输入。

3. 工厂练习将四项内容参数化（角色、系统提示词、工具和调用方式）。为了防止专用智能体在输入含义模糊时偏离自身领域，您会添加什么作为第五个参数？
B 部分（索引）将同样的思路用于语料库，而非其它智能体，使知识层成为一个智能体，通过查询接口封装一组数据。C 部分（深度智能体）会进一步构建一个 planner 智能体，由它在全新上下文中调度子智能体，并将其工作状态持久化到虚拟文件系统。

### 参考资料

- Xu et al., ReWOO: Decoupling Reasoning from Observations (2023)。本模块的工作流智能体采用了 planner / worker / solver 分解方式。
- Wang et al., Plan-and-Solve Prompting (2023)。这是更简单的前身：一次 LLM 调用写出计划，同一个 LLM 逐步执行计划。ReWOO 将 planner 与执行器分离。
- Madaan et al., Self-Refine: Iterative Refinement with Self-Feedback (2023)。迭代式多轮研究背后的模式：智能体评判自己的输出并重新运行，直到达到质量阈值。
- LangGraph。这是一个生产级框架，将本模块手动勾勒的工作流/状态机模式正式化。
